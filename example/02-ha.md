# 02 · High availability: replicas, HAProxy, the raft store

`deployments/compose/docker-compose.ha.yaml`, on top of the base file,
replaces the single in-memory catalog with two replicas that keep their
state in the 3-node KV cluster, behind HAProxy:

| Service | Local URL | What it is |
|---------|-----------|------------|
| `lb` | http://localhost:8181, http://localhost:8404/stats | HAProxy 3.4; answers to the name `catalog` inside the network |
| `catalog-a` | http://localhost:18181 | replica on `-store-backend raft` |
| `catalog-b` | http://localhost:18182 | replica on `-store-backend raft` |
| `kv1`–`kv3` | `localhost:23791`–`23793` | the raft KV cluster |
| `pyiceberg` | — | a Python container with PyIceberg 0.12 |
| `minio`, `trino` | as in [01-base.md](01-base.md) | unchanged; Trino now goes through HAProxy |

## Start and stop

```sh
make ha-up        # build and start, wait until healthy
make ha-down      # remove containers and volumes
```

With plain compose (the overlay's services are in the `kv` profile):

```sh
HA="docker compose -f deployments/compose/docker-compose.yaml \
  -f deployments/compose/docker-compose.ha.yaml \
  --env-file deployments/compose/.env --profile kv"
$HA up -d --build --wait
$HA ps
```

Everything in [01-base.md](01-base.md) — Trino, curl, Swagger UI, MinIO —
works unchanged on port 8181; the difference is that the catalog's state now
survives restarts and replica failures.

## HAProxy

http://localhost:8404/stats shows both replicas, their health checks
(`GET /readyz` every second, down after 2 failures, up after 2 successes)
and how many requests each served.

```sh
for i in $(seq 6); do curl -s -o /dev/null -w '%{http_code} ' localhost:8181/v1/config; done; echo
docker logs echpochmak-lb-1 2>&1 | tail -6     # one line per request, with the replica that served it
```

Each replica is also reachable on its own port, to compare them:

```sh
curl -s localhost:18181/readyz; curl -s localhost:18182/readyz
curl -s localhost:18181/v1/main/namespaces | jq .
curl -s localhost:18182/v1/main/namespaces | jq .   # the same state: it is in the KV store
```

## The catalog's state in the KV store

```sh
make build
export ECHPOCHMAK_KV_ENDPOINTS=localhost:23791,localhost:23792,localhost:23793
bin/kvctl status
bin/kvctl get cat/v1/ -prefix                 # namespaces, table and view pointers, idempotency records
bin/kvctl -json get cat/v1/tbl/ -prefix | jq -r '.[] | .key + "  " + .value'
```

The keys are `cat/v1/ns/…`, `cat/v1/tbl/<namespace>\x00<table>` and so on;
a table's value is its current metadata location. Writing to these keys by
hand bypasses every check of the catalog: read only.

## PyIceberg

The `pyiceberg` container has the client installed and the MinIO
credentials in its environment:

```sh
docker exec -it echpochmak-pyiceberg-1 python
```

```python
import os
import pyarrow as pa
from pyiceberg.catalog import load_catalog

cat = load_catalog("local", **{
    "type": "rest",
    "uri": "http://catalog:8181",          # HAProxy
    "s3.endpoint": "http://minio:9000",
    "s3.access-key-id": os.environ["S3_ACCESS_KEY"],
    "s3.secret-access-key": os.environ["S3_SECRET_KEY"],
    "s3.region": os.environ["S3_REGION"],
})

cat.create_namespace("py")
schema = pa.schema([pa.field("id", pa.int64()), pa.field("name", pa.string())])
tbl = cat.create_table("py.people", schema=schema)
tbl.append(pa.Table.from_pylist([{"id": 1, "name": "ann"}, {"id": 2, "name": "bob"}], schema=schema))

print(cat.list_tables("py"))
print(cat.load_table("py.people").scan().to_arrow())
print([s.snapshot_id for s in tbl.snapshots()])
```

The table is immediately visible to Trino:

```sh
docker exec echpochmak-trino-1 trino --execute "SELECT * FROM iceberg.py.people"
```

The writer used by the HA tests appends one row per step and prints what it
acknowledged:

```sh
docker exec echpochmak-pyiceberg-1 python writer.py --table py.log --writer demo --count 5
```

(The table must exist: create it first, for example with Trino:
`CREATE TABLE iceberg.py.log (writer varchar, seq bigint)`.)

## Failures to try

Kill a replica while writing; HAProxy routes around it:

```sh
docker exec echpochmak-pyiceberg-1 python writer.py --table py.log --writer a --duration 20 &
sleep 3; docker kill echpochmak-catalog-a-1; sleep 5; docker start echpochmak-catalog-a-1; wait
```

Kill the raft leader; a new one is elected in about a second:

```sh
bin/kvctl status                                    # note the leader, say 2
docker kill echpochmak-kv2-1
bin/kvctl -endpoints localhost:23791,localhost:23793 status
docker start echpochmak-kv2-1
```

Lose the quorum: both replicas report unready and HAProxy stops routing;
bring one node back and they recover:

```sh
docker stop echpochmak-kv1-1 echpochmak-kv2-1
curl -s localhost:18181/readyz                      # {"status":"unavailable"}
docker start echpochmak-kv1-1 echpochmak-kv2-1
```

A graceful stop drains: the replica reports `draining` for 3 seconds while
it keeps serving, then finishes the requests in flight:

```sh
docker stop echpochmak-catalog-b-1 & sleep 1; curl -s localhost:18182/readyz; wait
docker start echpochmak-catalog-b-1
```

## Idempotency across replicas

The first attempt goes to one replica, the retry to the other: the second
answer is the stored one.

```sh
KEY=$(uuidgen)
BODY='{"namespace":["idem_demo"]}'
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:18181/v1/main/namespaces \
  -H "Idempotency-Key: $KEY" -H 'Content-Type: application/json' -d "$BODY"
curl -s -D - -o /dev/null -X POST localhost:18182/v1/main/namespaces \
  -H "Idempotency-Key: $KEY" -H 'Content-Type: application/json' -d "$BODY" | grep -iE '^HTTP|replay'
```
